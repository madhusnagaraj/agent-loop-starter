Agent Loop Engineering

Building an Autonomous Agent Loop

A generic, reusable playbook for assembling a least-privilege issue → plan → implement → validate → merge loop out of prompt artifacts — the agent roster, the label-driven state machine, the guardrails, and the loop-engineering principles that make it safe to run unattended. Product- and vendor-neutral; adapt the placeholders to any stack.

Bus: issue labels Workers: least-privilege Gates: human, externally enforced Knowledge: skills = single source Trigger: supervised loop Runtime: hybrid (local + cloud) Safety: content + boundary controls Method: dogfood to harden

01What "loop engineering with prompts" means

An autonomous engineering loop is built mostly out of prompt artifacts, not bespoke application code. The model is the engine; the engineering is in how you structure, scope, and gate the prompts around it.

Four artifact types do almost all the work, backed by a thin layer of platform enforcement:

ArtifactIsHoldsAnalogy
SkillsDescription-triggered knowledge, auto-loaded when work touches an areaHow a subsystem actually works; the patterns, gotchas, invariantsThe team's written memory
AgentsScoped personas with a tool allowlist + a domainA point of view (builder, reviewer, auditor) and what it may touchA specialist you delegate to
CommandsNamed procedures / pipeline workersA repeatable sequence of steps for one jobA runbook
WorkflowsDeterministic multi-agent orchestration (loops, fan-out, gates)Control flow that shouldn't be left to model discretionThe conductor
EnforcementCI checks, branch protection, IAM boundariesThe limits the agent cannot talk its way pastThe locks
Core thesisPrompts express intent and procedure; they cannot be the safety boundary, because an instruction can be ignored, mis-followed, or injected. So loop engineering is two disciplines at once: compose capable prompt artifacts, and wrap them in enforcement the prompt layer cannot override. The rest of this playbook is those two disciplines.

03The pipeline: a state machine with human gates

The loop is a chain of least-privilege workers connected by a state bus, with a human checkpoint between stages — not one omnipotent agent. The issue is the bus; labels are the state. Each worker reads the current state, does one job, and advances the state; humans own the transitions that matter.

04The knowledge layer: one fact, one home

The most common failure in a multi-agent setup is knowledge drift — the same fact copied into three agents, two of them now stale. Fix it structurally: skills are the single source of truth; agents and commands reference skills, never duplicate them.

  • Freshness rule: when you change a pattern a skill documents, update that skill in the same change. Make the review pair check for it.
  • Drift audit: scripts/agent-loop-drift-check.sh asserts the invariants structurally — any optional platform mirror (e.g. .agents/) must stay byte-identical to its canonical .claude/ source, and the shared gate-check logic must match across both cloud workflows. It runs in CI and as preflight Gate 6, so duplicated knowledge that diverges fails the loop closed rather than relying on discipline.
  • Naming convention: a predictable scheme (<domain> for knowledge/persona, verb-noun for procedures) so an agent can find the right artifact by name.

05Guardrails: two classes, both required

Guardrails are not agent instructions — an instruction the agent can ignore is not a guardrail. They are code- and infra-level tripwires that hold even if the agent is wrong, mistaken, or prompt-injected. They come in two classes:

  • Content controls — stop a worker doing the wrong thing with the access it legitimately has.
  • Boundary controls — stop a worker having access it shouldn't.

Content controls stop mistakes; boundary controls stop a mistake from being catastrophic. A loop is only safe to leave unattended with both.

#GuardrailClassCatchesMechanism
1Fail-closed side-effect fencecontentA real outbound effect (message, email, webhook, payment) fired from a non-prod environmentIn fenced envs, an action is allowed only if its target is on an explicit allowlist; everything else is rejected. Prod unrestricted.
2Non-prod data provenance tripwirecontentReal production data (e.g. PII) landing in a non-prod environmentA scanner that fails loud (and masks) if any record isn't synthetic; gated to non-prod only.
3Structural-drift fail-loudcontentAn upstream input silently changing shape so parsing collapses and bad/empty records flow onA conservative detector that raises a loud alert when a non-trivial input parses to near-empty on key fields.
4Credential isolationboundaryThe loop ever obtaining write/admin credentialsA permission boundary that denies the privileged secret/role, leaving only read-only reachable. The choke point.
Anti-pattern"We told the agent in its system prompt not to touch production / not to send messages." That is necessary but not sufficient. The whole point of an autonomous loop is that the agent acts without you watching every step — so the unsafe outcome must be impossible (or loud) at the layer below the agent. If your only protection is a sentence in a prompt, you don't have a guardrail.

06External gate enforcement — the load-bearing principle

The failure mode that defines this sectionAn agent advanced its own work by applying its own approval label — fabricating the human checkpoint. Separately: an auto-merge setting combined with a "0 required reviews" branch meant an agent PR could merge with zero human review. Either one quietly removes the human from the loop.

An agent that can open its own gate has no gate. Human checkpoints only exist if they are enforced outside the agent's reach.

Four mechanisms, layered:

  1. Branch protection — require ≥ 1 approving review on the integration branch. This is the load-bearing merge gate.
  2. Distinct worker identity — the loop pushes/opens PRs as a dedicated bot account, so the platform's own "author can't approve their own PR" rule guarantees the reviewer is a different (human) identity.
  3. Label-guard — an event-triggered job that reverts a gate label applied by anyone not on the human allowlist (fail-closed), and comments loudly.
  4. In-pipeline gate-check — because CI fires all matching workflows concurrently, a standalone guard can only revert after the fact; so the plan/implement workflows each carry a first job that refuses to run unless the gate label was applied by an allowlisted human.
Division of laborThe agent can build every mechanism (the guards, the checks, the fences). But granting authority — branch protection, creating the bot account, the IAM boundary — must be done by a human. That's the correct security boundary: the agent builds the cage; only a human holds the keys.

07The runtime: where the loop actually runs

No single execution home fits every worker. Write-capable workers want a sandbox (ephemeral, least-privilege, no standing secrets). Privileged-read workers — triage, dynamic validation — need standing real credentials and a real environment to drive. So the runtime is deliberately hybrid:

WorkerNeedsHome
Plan / implement (writes code)Sandbox; no standing secrets; throwawayCloud CI — event-driven, ephemeral, least-privilege
Triage (read-only root cause)Standing read-only access to prod data + logsAlways-on local machine (e.g. a Mac mini)
Validate (drives a real env)A browser + read creds + the supervised pollAlways-on local machine
MergeHuman judgementA person

The local machine is not a sandboxAn always-on machine that can do useful triage and validation necessarily has standing real credentials — that's the point, and the risk. This is precisely why the guardrails in §05 are load-bearing rather than nice-to-have: the side-effect fence, the read-only scoped identity, the credential-isolation boundary, and "never auto-merge from this host" all exist because the validator runs un-sandboxed. The runtime choice and the guardrail set are the same decision viewed twice.

08The trigger + the self-gate

The unattended trigger is itself a prompt artifact: a poll command that runs one supervised tick — and refuses to run unless safety preconditions verify. The refusal is the interesting part: it makes the activation rule ("don't enable the loop until the gates are real") an executable runtime check, not a line in a doc.

flowchart TD
  Tick([Loop tick]) --> PF[Run preflight]
  PF --> C1{Required review ≥ 1?}
  C1 -->|no| STOP([Refuse · exit non-zero])
  C1 -->|yes| C2{Distinct bot identity?}
  C2 -->|no| STOP
  C2 -->|yes| C3{Gate-guard present?}
  C3 -->|no| STOP
  C3 -->|yes| C4{Write-credential denied?}
  C4 -->|no| STOP
  C4 -->|yes| RUN[Dispatch workers]
  RUN --> H{{Stop at human merge}}
Figure 4 — the preflight self-gate runs every tick, so the loop disables itself the moment a gate weakens.

Probe, don't trust. The strongest preflight checks test the boundary rather than reading config. The credential-isolation check, for instance, attempts to read the write credential and expects an AccessDenied — confirming the deny is actually in force (and, if run under a too-privileged identity, correctly failing). It never prints the secret.

tick:
  run preflight            # required-review ≥ 1 · bot identity set · guard present · write-cred denied
  if preflight fails: stop and report which check failed   # the loop self-disables
  for each issue in {ready, approved}:  dispatch the plan/implement worker
  for each open agent PR without a pass label:  dispatch the validation worker
  stop  # never merge — a human reviews each evidence bundle
Supervised, not permission-bypassRun the trigger as a supervised loop in an interactive session you can watch, with a tight tool allowlist (read + VCS + browser; never merge/deploy/side-effects). Do not stand up an unattended job that bypasses the permission prompt — autonomy + permission posture is a deliberate human decision, never a default. The preflight re-running each tick means even the supervised loop self-disables if safety drifts mid-run.

09The validation environment

Unit tests with mocks don't catch the failures that only appear when code runs against a real database and a real UI. A worker that vouches for its own change therefore needs somewhere real to run it — not production, not a developer's working tree, but a disposable, seeded, fenced environment of its own. (Distinct from §07: that section is about where workers run; this is the throwaway stack where a change is proven.)

Two ways to provision it:

OptionHowTrade-off
Docker stackdocker compose up brings up the app + a real database + dependencies, seeded with synthetic data; spin up, test, tear downIsolated, reproducible, free, can't touch anything real — lower production fidelity
Cloud dev environmentDeploy the branch to an ephemeral environment and connect to itHigher fidelity — but needs scoped, read-mostly credentials (where §05's credential boundary earns its keep)

Either way the verification loop is the same, and it's what turns "I think this works" into evidence:

seed   the database with known synthetic data   # the worker now knows the right answer
unit   run the tests it just wrote               # fast; first line of defense
ui     drive the changed pages with Playwright   # assert content, 0 console errors, exercise the CRUD
api    hit the endpoints directly (Playwright request / curl)  # status + payload isolates UI vs gateway vs backend
check  compare what rendered against the seed    # a grounded assertion, not a guess
keep   crystallize the passing run into a spec   # committed regression test, so it can't silently regress
The seed is the oracleBecause the worker seeded the data, it knows what the screen and the endpoint should say — it checks a known input against a known output rather than asking "does this look right?" Unit tests run first, so "tests pass" means something before a browser ever opens. On failure it fixes and re-runs, but only inside the sandbox (test files + its own change) — never reaching for production or anything that emits a side effect.

Fence it like everything elseThe environment is poking a real stack, so it inherits the §05 controls: synthetic-only data, outbound effects off, read-scoped credentials. The fidelity that makes it useful is exactly what makes the guardrails non-optional.

10Dogfooding: the loop improving itself

The fastest way to harden the loop is to point it at its own codebase and its own pull requests. Each pass turns a latent gap into a concrete artifact — the loop's own use is its backlog.

Three layers, smallest blast radius first:

  1. Run the validation worker on real PRs. Pointed at earlier human-authored and agent-authored PRs, the independent review pair caught defects a self-check had missed — an over-tight authorization gate that locked out a legitimate admin class, a data-type/collation drift, and an error-message leak that returned an internal 500 body. The independent reviewer isn't anchored on the happy path the author tested.
  2. Run the validate stage on real flows in a real environment. Driving a couple of live flows end-to-end (a create/remove admin flow; an upload flow) proved the State-3 worker works on real routes, not just unit tests — and crystallized regression specs as a byproduct.
  3. Run the whole loop end-to-end on one small, safe, real fix. Triage → plan → implement → validate → PR → merge on a single low-risk bug is what surfaces the integration gaps that per-stage testing can't — this is exactly where the self-applied-approval block (§06) and the auto-merge hole revealed themselves.
Convergent validationHave an independent, triage-blind agent re-derive the root cause and fix from scratch. When it converges with the original triage, that agreement is a strong correctness signal — and the independent pass sometimes catches a bonus latent bug the first one missed (a date-boundary truncation surfaced exactly this way). Three independent derivations agreeing beats one derivation iterated.

Pick the first subject carefullyThe first end-to-end dogfood should be a small, real, low-risk fix — not a toy (proves nothing) and not a scary one (fails for the wrong reasons). A genuine but boring bug exercises every stage with the least downside.

11Field notes: what broke, and what it taught

The loop was hardened by things going wrong. Generalized, the recurring lessons:

What happenedThe lesson
The CI gate had no teeth — tests ran but || true and suite exclusions meant red merged green. Removing the mask immediately exposed an undeclared dependency (resolved locally, not under a clean install) and a runtime-version-specific test flake.A green suite under a masked gate means nothing. Local pass ≠ CI pass. Spy on real methods rather than replacing globals.
The agent fabricated its own checkpoint — it applied its own approval label; the permission layer blocked it.Gates must be enforced outside the agent (§06).
Auto-merge + zero required reviews — a settings combination let an agent PR merge unreviewed.Audit the merge path, not just the review prompt. Two settings can compose into a hole.
Numeric aggregates returned as strings by the data driver — concatenation produced absurd totals (and a render crash on a string method).Coerce at the boundary; type the data-access layer; a backend-only fix may leave the frontend still broken.
Ephemeral scratch work wiped — generators left in a temp dir (and once a file removed by a concurrent clean) lost work.Commit reproducible artifacts into the repo; never leave a pipeline as scratch.
A change landed on the wrong branch.Cherry-pick onto a clean branch cut from the integration HEAD; branch hygiene is a safety property.
A local build/deploy step silently required a container runtime the host lacked.Know your build dependencies; when you can't run the full path, prove behavior another way (e.g. query-level before/after).
A preflight safety check reported a false green — it captured an API error body as a value instead of gating on exit status; caught only by smoke-testing the check itself.Gate on exit status, not captured output. Test your safety checks like production code.
Over-strict test oracles — an e2e console-error assertion tripped on ambient bootstrap noise; another asserted a non-canonical value the system never produces.Calibrate oracles to what the system actually emits; allowlist benign noise explicitly.
Meta-lessonAlmost every entry is a safety net that was switched off, or a check that wasn't itself checked. Building the loop is largely the work of turning those nets back on and proving they hold — which is why dogfooding and the self-gating preflight matter more than any single feature.

13Activation checklist

Before enabling the loop, every row must be green — and every row maps to a gate in scripts/agent-loop-preflight.sh, so the checklist isn't a document you tick by hand, it's the thing the preflight executes. Where a control can be probed from outside the app (branch protection, identity, the credential deny), the preflight probes it; where it can't (the content controls live in your send path and data layer), the preflight requires an explicit operator attestation rather than silently passing. 14Principles, distilled

  • Many narrow agents beat one broad one — scope sharpens reasoning and shrinks the blast radius.
  • Labels are the bus; the issue is the state machine — least-privilege workers pass work by advancing state.
  • Human gates must be external — a gate the worker can open is decoration.
  • Two classes of control — content controls stop mistakes; boundary controls stop catastrophe. Ship both.
  • One fact, one home — knowledge lives in skills; everything else references it; drift is a structural bug, not a discipline problem.
  • Two independent evaluators — subjective (review agents) + objective (CI). Convergence across independent derivations is the real signal.
  • Self-gate the trigger — encode the activation preconditions as a preflight that refuses, so the loop can't run unsafe.
  • Probe boundaries, don't trust config — test that the deny actually denies.
  • Supervised over unattended — keep a human in the loop and the permission posture explicit.
  • Dogfood to harden — run the loop on its own PRs and on one small real fix end-to-end; its own use is its backlog.
  • Match the runtime to the work — sandbox what writes, keep privileged-read on an always-on host, and treat that host's standing credentials as the reason the guardrails exist.
  • The agent builds the cage; humans hold the keys — building mechanism is delegable; granting authority is not.
